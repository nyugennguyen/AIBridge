# Milestone 0 threat model and non-overridable safety floor

Status: M0.6 security-review artifact for contract family `aibridge.orchestration`, schema version `1`. This is a review of the frozen architecture and contracts, not a claim that production controls exist. The milestone lead and M0.9 reviewer own the integrated gate decision.

Sources: [current-state inventory](../architecture/milestone-0-current-state-inventory.md), [ADR 0001](../adr/0001-canonical-domain-and-module-boundaries.md), [ADR 0002](../adr/0002-versioned-contracts-and-adapter-boundaries.md), [ADR 0003](../adr/0003-event-store-and-idempotency.md), [ADR 0004](../adr/0004-controller-leases-and-recovery.md), [M0 plan](../implementation-plans/milestone-0-architecture-and-migration.md), and the orchestration/runtime/terminal schemas and interfaces under `src/`.

## Scope and trust assumptions

The reviewed system is a Tailscale-private orchestrator with a node-owned runtime and terminal, project-scoped work, digest-bound approvals, a fixed run authority, and durable command/fence records. M0 contributes definitions, pure translation, and tests; it must not introduce execution, enrollment, terminal streaming, SQLite writes, or controller election.

Assume the host OS, its administrator, the daemon executable, and the authority's protected storage are trusted. A local attacker who can replace the daemon or modify its protected database can defeat application checks; a checksum or schema parser does not solve that compromise. Treat a compromised remote node as hostile even if its key remains valid: constrain it to its enrolled identity and explicit projects, revoke it, and do not treat its self-reported completion as independent verification of work. Assume networks drop, delay, duplicate, reorder, and partition; local processes and disks fail; clocks drift or jump; agents and repositories contain adversarial content. A Tailscale connection provides reachability, not user identity, enrollment, project membership, or approval.

## Assets, actors, and boundaries

Protected assets are node/private enrollment keys, legacy bearer and provider credentials, project files, prompts/context/memory/artifacts, approval records and exact approved content, runtime sessions and terminal input, run history and source attribution, lease epochs, receipts and uncertain-effect evidence, backups, and bounded CPU/disk/network/provider expenditure. Availability matters, but uncertainty must not permit unauthorized work or duplicate effects.

Actors include an authenticated operator, project administrator, enrolled worker/controller, fixed authority, local runtime adapter, terminal client, legacy token holder, untrusted agent session, repository/artifact author, unenrolled tailnet peer, revoked or compromised node/controller, and local unprivileged process. A field such as `actor.kind: user` or `controllerNodeId` is an assertion to verify, never credentials. A controller may coordinate approved work; that role does not confer operator approval, project administration, secret export, or ownership of another node's processes.

The principal boundaries are: operator to local daemon; tailnet peer to enrolled identity; authenticated identity to project/run authorization; controller to fixed authority; command admission to worker effects; daemon to runtime/provider and terminal backend; untrusted output to history/context/UI; filesystem/database to validated records; and legacy records to inert canonical history. The following inventory assigns both parsing and authority ownership. "Future" means an implementation gate, not a permission to bypass the check until then.

## Threats and mitigations

Severity describes the consequence if the control is absent: **Blocker** prevents safely enabling the affected capability; **High** permits unauthorized effects/disclosure or irrecoverable audit loss; **Medium** damages bounded availability or confidence; **Low** is limited disclosure/usability impact. Later-milestone obligations are not presented as current test results.

| Threat | Consequence / severity | Required mitigation and owning gate |
| --- | --- | --- |
| Forged node/controller/user identity; compromised enrolled controller | Unauthorized dispatch, approval, query or credential access — Blocker for mesh | Revocable enrolled peer identity, protected keys, fixed-authority proof, separate operator authority and exact project/capability checks. Never promote actor JSON, legacy token possession or tailnet reachability into identity. Controller compromise cannot forge separately verified approvals. M1 local user; M4 mesh. |
| Replay, concurrent duplicate delivery, changed command under same key, forged ack | Duplicate launch/prompt/permission response or lost delivery — Blocker for remote retry | Full canonical-command fingerprint, scoped stable key, durable authenticated receipts, original result on exact duplicate, conflict on mutation, transactional outbox/inbox. Keep receipts/tombstones while replay remains possible. Fresh IDs cannot bypass dispatch/session/request uniqueness. Ambiguous runtime outcomes block replay. M1/M3/M4. |
| Stale controller, forged higher epoch, partition or clock rollback | Split brain and conflicting work — Blocker for takeover | One fixed authority/store, durable monotonically increasing worker fence, verified lease-holder proof and bounded clock uncertainty; recheck immediately before effects. ADR 0004 takeover waits for old expiry and every relevant worker's reconciliation. No election/replica promotion/epoch reset. M3/M4. |
| Project-path traversal, symlink replacement, hostile native handle or executable path | Read/write/execute outside project or session — High | Worker resolves explicitly configured project/path binding and checks it again at the process boundary, rejecting traversal, wrong node and symlink escape. Use platform-safe directory/handle ownership so a check/use race cannot redirect work; reject operations where that guarantee is unavailable. Paths and handles are never derived from untrusted opaque IDs. M1/M2/M3.8. |
| Approval-envelope mutation, misleading approval preview, mutable role/rule/context | Work differs from approved target, prompt, model, permissions or content — Blocker for launch | Render and approve the exact complete canonical envelope, recompute digest at worker, authenticate approval, resolve and verify context bytes, intersect policy. Any material change/new epoch before execution requires new dispatch/attempt/evaluation. Show untrusted text as text so it cannot impersonate approval controls. M0 digest tests; M1/M3/M5/M6 enforcement. |
| Terminal input hijack, attachment takeover, buffered writes after ownership loss | Input reaches wrong process, bypasses approval or executes under revoked identity — Blocker for interactive input | Default read-only, explicit audited ownership/takeover, one owner serialized per terminal, authenticated client binding, current access check on every write, invalidate queued writes on loss/revocation. Native terminal input must remain within original permissions; if provider/sandbox cannot enforce blocked permissions, deny interactive writes in that state. Detach never kills. M1/M4. |
| Malicious agent output, repository instructions, fake completion or poisoned memory | Prompts treated as policy; false success unblocks destructive work — High | Treat output as data; normalize and authenticate provider/session observations, require reliable completion evidence, retain unknown on ambiguity. Memory acceptance is separate authorization; provenance/visibility survives summaries and supersession. Escape output in approval/audit UI; terminal control sequences cannot become host clipboard, shell or control-plane actions. M1/M2/M3/M5. |
| Secret leakage in prompts, logs, events, metadata, memory, artifacts or callbacks | Credential theft and cross-project disclosure — High | Keep provider/node secrets local and purpose-scoped; redact/reject sensitive content before persistence/transmission and before approval hashing. Apply reader/sensitivity checks and explicit context manifests. Key-name filters and secret scanners alone are insufficient; do not log free-form payloads. Rejected input/error handling must not echo secrets. M1/M3/M4/M5/M7. |
| Oversized nested events/artifacts, decompression, endless streams, fan-out or pathological rules | Memory/disk/network/provider-cost exhaustion — High | Enforce total encoded-byte/depth/collection limits before expensive parsing and per-principal/project quotas; bounded queues/retries/stream buffers, backpressure, concurrency/budget caps and disk-low refusal. Positive safe byte counts do not imply a supported artifact size. Bounded pattern semantics, no arbitrary code/unchecked regex evaluation. M1/M3/M4/M5/M6; M7 load evidence. |
| Corrupt, truncated, maliciously edited or downgraded persisted state | Lost approvals/fences/receipts, invented history or reexecution — Blocker for recovery | Strict version parsing, complete transaction constraints, integrity/provenance checks, protected storage, visible quarantine and verified backups. Never silently use empty defaults for safety state. Projection replay creates no effects. Stale authority backups cannot reset epochs or erase acknowledged work. M0 migration contract; M1/M3/M4/M7. |
| Arbitrary callback/artifact URL, redirect or DNS change | SSRF, credential forwarding and internal service access — High | Explicit recipient/service allowlist tied to authenticated peer/project; validate scheme, origin and resolved destination at connection time; reject disallowed redirects and never send credentials to unrelated origin. OpenCode stays loopback on port 4096; bridge binds approved loopback/Tailscale address. M1/M3.8/M4/M5. |
| Cross-project queries, stream cursors, session restore or correlation collisions | Disclosure/control of unrelated work — High | Every read and effect resolves canonical ownership from trusted records, including nested references; IDs/digests are not access tokens. Scope caches, subscription channels, receipt reads and legacy mappings. M1/M3/M4/M5. |

## Non-overridable, testable invariants

These constraints apply to roles, rules, approvals, adapters, migrations, terminal interaction and administrative recovery. A trusted operator may supply missing authorization but cannot authorize bypassing these invariants inside the orchestrator. Host-level administrative actions remain outside its claimed enforcement boundary.

| ID | Required property / observable failure result | Implementation owner |
| --- | --- | --- |
| SF-01 | No read or effect is authorized from claimed actor/node/client/lease IDs alone. A forged or revoked principal yields a safe denial before data/effect access. | M1 application/terminal; M4 identity middleware |
| SF-02 | A command, referenced session, path binding, task, artifact and context record must resolve to the authorized project/run/node. Any cross-scope substitution denies access and has zero effects. | M1 application; M3 kernel; M4 worker; M5 context |
| SF-03 | Execution uses the authorized resolved project directory and owned runtime handle at the actual effect boundary. Traversal, symlink escape/replacement, wrong installation or unowned handle cannot launch/write. | M1 node/terminal; M2 runtime; M3 compatibility |
| SF-04 | Effective capabilities are the intersection of the system floor and every applicable project/role/dispatch restriction. No approval, pre-approval or `allow_always` response restores a denied capability or removes destructive/external safeguards. | M1 local gate; M3 policy; M6 rules |
| SF-05 | Launch requires authenticated approval for the exact recomputed envelope/dispatch digest and current policy. Context bytes must match referenced digests. A mutation of any field or underlying context fails; revision gets new identity/attempt and approval. | M0 hashing contracts; M1/M3 execution; M5 context |
| SF-06 | A worker admits effects only under a proven fixed-authority lease for its authenticated controller and durable highest epoch. Lower epoch or same epoch with different holder/lease fails; expiry and conservative clock bounds are checked immediately before effects. | M3 local gate; M4 lease/worker |
| SF-07 | Same scoped command ID/content produces the original receipt, no additional intent/effect; changed content conflicts. New IDs cannot create a second session for a dispatch or consume one permission request twice. | M1 journal; M3 kernel; M4 inbox |
| SF-08 | Receipt/event/head/projection/outbox commit is atomic. Acknowledgment and external invocation cannot precede required durable admission. An uncertain launch/prompt/response is reconciled, never blindly replayed. | M1 store/adapter; M3 store/kernel; M4 transport |
| SF-09 | Takeover cannot resume while any relevant worker, old command or possible effect is unaccounted for. Clock/fence/store loss blocks new effects; no automatic election, epoch reset, stale-backup promotion or recovery bypass exists. | M3 restart; M4 authority/recovery |
| SF-10 | A terminal has at most one input owner. Read-only, detached, revoked and former-owner channels cannot write, including buffered writes after takeover. Attachment cannot widen runtime permissions or bypass a blocked permission/recovery gate. | M1 terminal/runtime; M4 terminal gateway |
| SF-11 | Detach/TUI/controller loss preserves node-owned sessions. Restore returns a proven existing execution; missing projection or terminal silence never launches a replacement or marks success. | M1/M2 runtime; M3/M4 recovery |
| SF-12 | Raw terminal streams, credentials, unredacted secrets and raw environment values never enter domain events, application logs, memory or diagnostics. Runtime metadata is sanitized by value. Protected artifact/context transmission requires authorized scope and sensitivity. | M1 adapters/logging; M3 events; M4 transport; M5 data; M7 diagnostics |
| SF-13 | Agent output cannot create authority, approval or accepted memory by assertion. Success requires verified declared completion evidence; otherwise retain `unknown`/blocked state. | M1/M2 runtime; M3 kernel; M5 memory |
| SF-14 | Unknown/missing canonical versions, corruption, counter overflow, sequence gaps and unsafe rollback produce explicit failure/quarantine, not empty state, silent downgrade, skipped evidence or execution. Replay never emits runtime side effects. | M0 parser/import contract; M1/M3 store; M4 fence; M7 restore |
| SF-15 | Every ingress and producer has enforced finite limits for total bytes, buffering, queue/concurrency/fan-out, retries and retention. Rejection/backpressure is bounded and cannot exhaust the audit/fence store. | M1 services; M3 scheduler; M4 transport; M5 data; M6 budgets; M7 load |
| SF-16 | Legacy translation preserves or narrows source/capability/project restrictions, retains IDs as external correlation, imports active work inertly, and never converts plan text/shared token into canonical approval/node authority. Repeated identical import is inert/idempotent; changed input conflicts. | M0.7 mapping; M3.8 importer/gateway |
| SF-17 | Outbound credentials are bound to an authorized recipient; caller-controlled URL/redirect/locator cannot send them elsewhere. Public-interface binding and public OpenCode exposure fail configuration preflight. | M1 node/config; M3.8 callbacks; M4 transport; M5 artifacts |

The runtime operation context omits command deadlines and proof material by design: its IDs must resolve through the trusted worker admission service to the original unexpired command, lease, approval and receipt. A runtime adapter exposed directly to untrusted callers without this gate violates SF-01/SF-06. Likewise, terminal channel writes have no per-write context argument; the backend must bind the channel to an authenticated client and recheck live ownership/policy on every write. An attachment cannot authenticate itself by supplying a client ID.

The M0 schemas enforce shape, bounds and selected nested relations. They deliberately do not prove hash equality for all stored data, database relationships, live authorization, actor legitimacy, path containment, secret absence, reliable completion or state transitions. These service checks are mandatory even when parsing succeeds.

## Ranked findings and disposition

No new M0 architecture/contract blocker was found in this review. ADRs 0001–0004 specify the required authority, digest, durability, uncertainty and takeover behavior without claiming M0 implements it. Production launch/terminal/mesh approval is withheld until the applicable gates above pass. The existing legacy bridge has concrete risks below; accepting a contracts-only M0 gate does not resolve or accept those risks for broader deployment.

F-01–F-06 are outside this document-only task's permitted changes. The milestone lead must explicitly record their pre-existing, unchanged status and owning release gates; they are not closed by this review. An implementation that newly enables an affected path without remediation has a release blocker. No test here contacts a live node, launches a runtime, changes a credential or exploits a filesystem write.
